* Goal, scope, acceptance

** Goal
Reduce wall-clock time and token spend of a typical =lead= run in the ECA agent
bundle shipped by this dotfiles repo (=modules/programs/eca/=), without losing
the guarantees the user actually relies on: evidence-based verdicts, one writable
owner per path, and no "done" claim without observed proof.

The dominant cost is *not* model choice. It is the unconditional pipeline
(researcher -> architect -> specialist -> verifier -> reviewer -> security ->
remediator -> re-verify -> summary), the hook that forces extra =lead= turns, and
the ~1715-word =lead.md= plus ~995-word =AGENTS.md= replayed on every turn and
every spawn.

** In scope
- =modules/programs/eca/agents/*.md= (roster, frontmatter, prompt bodies)
- =modules/programs/eca/AGENTS.md=
- =modules/programs/eca/_hooks.nix=
- =modules/programs/eca/skills/implementation-planning/SKILL.md=
- =modules/perSystem/checks.nix= (one new check)
- new =modules/programs/eca/_workflow-check.nix=

** Non-goals
- Do not change the pinned ECA version (=ecaVersion = "0.157.0"=) or the release hashes.
- Do not change =flake.lock=, lockfiles, or vendored/generated files.
- Do not change =toolCall.approval= allow/deny regexes in =modules/programs/eca.nix=.
- Do not change =nixMcp=, =version-git-approval=, or any Git safety behaviour.
- Do not touch =modules/rice/=, hosts, or any module outside the list above.
- Do not activate home-manager or switch the system as part of this work.
- Do not run Git writes. The user writes commits.

* Decisions, assumptions, open questions

** D-01 Two tiers, decided by lead during its first inspection
*Decision.* Replace the unconditional pipeline with two tiers. =lead= picks the tier
during its first normal inspection of the request — not in a dedicated triage turn
and not via a delegated triage call — and states the tier plus a one-line rationale
inside the implementation spawn task.

*Fast tier entry rule (all must hold, unknown => full):*
1. The change is confined to at most two existing writable files in one module.
2. Relevant paths are identifiable from the request plus at most one bounded source inspection.
3. It adds no public/shared interface, no dependency, no generated artifact, no migration, no cross-module wiring.
4. It does not touch security, permissions, secrets, unsafe-command policy, ECA hooks, agent permissions, concurrency, or persistent state.
5. There is no designer-created Org plan in play.

*Fast pipeline:* lead inspects named files -> one owning specialist -> =verifier=
with the narrowest sufficient project check and per-criterion evidence -> lead reads
the actual report and answers. No architect, no research agent, no reviewer, no
summary, no =eca__task=.

*Fast escalation:* a FAILED or UNVERIFIED verifier, a surprise path, or a newly
discovered shared contract escalates to full before any further implementation.
Fast must never close on an unverified change.

*Full pipeline:* lead reads entry points, spawns =researcher= only for a bounded
missing fact -> =architect= (skipped when a usable designer Org plan already supplies
the packets) -> specialists in disjoint dependency-ordered groups -> =verifier= over
the integrated change -> =reviewer=, with =security= in parallel when classified
required -> lead consolidates findings and returns each one to its *original*
specialist -> repeat affected verification/review until the latest actual reports
are PASSED/CLEAR or a blocker is reported -> lead writes the final report itself.

*Deliberately relaxed:* fast changes get no independent reviewer, no architect plan,
no tracker persistence. *Preserved:* single writable owner, explicit
PASSED/FAILED/UNVERIFIED evidence, project checks over inferred success, and the
designer-plan section checkpoint contract (including its mandatory per-section
security review).

=solo= and =researcher=. =solo= is the cheapest possible mode — one agent, no
delegation — and removing a manually selectable entry point the user may rely on is
a UX regression that works against the stated goal. See D-04 for the research pick.

** D-03 Model and variant retiering
The user's directive: =gpt-6-luna= for less complex roles; current models are fine
for complex ones. This plan therefore changes model identity in only two places and
otherwise *removes reasoning variants*, which is where the latency actually is.

| Agent | Now | Planned | Why |
|---+---+---+---|
| lead | sol / high | sol / *none* | Highest turn count in the system; =high= is paid on every orchestration turn for work that is mostly routing. |
| architect | sol / high | sol / high (unchanged) | Infrequent, consequential interface and ownership design. |
| designer | sol / high | sol / high (unchanged) | Durable multi-section plans. |
| debug | sol / high | *luna* / none | Bounded reproduce-hypothesise-verify loop; it delegates the hard parts. |
| version | sol / high | sol / *none* | Keep the stronger model for Git authority; drop perpetual =high=. |
| prreview | sol / high | sol / *none* | Reconciles a diff plus subagent reports; =high= is not load-bearing. |
| solo | sol / none | unchanged | Does everything alone; needs the capability. |
| backend, frontend, java, scala, nix-home-manager, rice-quickshell | 5.3-codex | unchanged | "What it's currently using" for the complex role. Changing all six at once is an unforced quality risk; revisit only after AC-11 measurement. |
| verifier, reviewer, researcher | luna | unchanged | Already the cheap tier. |
| security | claude-sonnet-5 | unchanged | An independent model lens is the point of this gate, and it now runs far less often. |
| explorer, remediator, summary, docs, refactorer | - | deleted | See D-02. |

Net effect: =variant: high= survives only on =architect= and =designer=.

*Unverified assumption:* that =github-copilot/gpt-6-luna= and =github-copilot/gpt-6-sol=
are currently available to this account with these exact identifiers, and that
dropping =variant= is accepted (rather than erroring) by ECA 0.157.0. SEC-01 probes
this before anything is edited. If a model is unavailable, *stop and report* — do not
silently substitute.

** D-04 Research consolidation picks =researcher=, not =explorer=
*Observed anomaly.* An =eca-info= inspection of the running server lists subagents as:
=architect — model: github-copilot/gpt-6-sol=, =researcher — model: github-copilot/gpt-6-luna=,
=verifier — model: github-copilot/gpt-6-luna=, plus =explorer= and =general= with
*generic built-in descriptions and no model attribution*. The description shown for
=explorer= ("Codebase search specialist...") is *not* the description in
=modules/programs/eca/agents/explorer.md= ("Focused read-only explorer for iterative
architecture research").

*Inference (unverified).* ECA 0.157.0 ships a built-in =explorer= subagent whose name
collides with the bundle's =explorer.md=, and the built-in appears to win. Consolidating
research onto =explorer= would therefore risk routing all research through a prompt and
model this repo does not control.

*Decision.* Delete =explorer.md=; make =researcher= the single read-only research role;
add =architect= to =researcher.spawnableBy= (final list: lead, architect, debug,
designer, version, prreview). SEC-01 confirms or refutes the collision; if it is
refuted, the choice is cosmetic and this plan still stands.

** D-06 Per-spawn token discipline
Added to =lead.md= and the specialist prompts:
- Lead packets must carry exact paths, pertinent line ranges, and the relevant snippet or symbol, plus acceptance examples, owner, cwd, and the literal intended checks.
- A specialist inspects its target and only the necessary neighbours. If the packet is insufficient it asks or returns BLOCKED rather than exploring the repo.
- Routine specialist / researcher reports: ~200 words plus bounded evidence entries. Reviewer findings: one line each. Lead's normal final report: ~150 words.
- Verifier runs the *narrowest sufficient* command set for fast work; full initial verification still covers the complete integrated change; later passes cover failed and affected checks only.
- No cap ever permits omitting a failure, a literal check result, or an UNVERIFIED criterion.

** D-07 Hook retuning
Strictly within the existing JSON contract.
- =lead= puts a standalone line =Workflow tier: fast= or =Workflow tier: full= in every implementation and architect spawn task, matched by =record= exactly the way =Security review: required= already is.
- =record= writes =tier-fast= or a *sticky* =tier-full= marker. Missing or malformed => full. A later full assignment upgrades fast to full; fast never downgrades full.
- Missing or malformed security classification fails closed to =security-required=; an explicit =required= line always wins.
- Branch 1 (implementation without verifier): *keep, both tiers.*
- Branch 2 (verifier without reviewer): *keep, full tier only.*
- Branch 3 (security required but not invoked): *keep, both tiers* — so a contradictory "fast + security required" assignment cannot bypass security.
- Branch 4: *delete.* Invocation markers never justify another turn.
- =.follow_up_active= suppression and =version-git-approval= stay untouched.
- =implementationAgents= loses =refactorer|docs|remediator=.

** Open questions (none blocking)
- OQ-01: after AC-11 measurement, should the six implementation specialists move from =gpt-5.3-codex= to =gpt-6-luna=? Deferred on purpose; it is a quality experiment, not a correctness change.
- OQ-02: should =security= drop to =gpt-6-luna= once it runs only on risk-classified changes? Deferred; keeping an independent vendor is the point of the gate.

=nix build .#nixosConfigurations.shitbox...toplevel= fails for a reason unrelated to
this change set; or any path would be written by two workstreams.
